# the-one-engine-install-branch-carries-ten-lint-findings

A round that stands alone, the way a defect found and fixed does. The branch
`fix/one-engine-install-at-a-time` makes a launcher build one engine at a time
per key, keeps one cargo target directory for every key, and resolves the cache
root absolute before the build runs elsewhere. Its four commits are sound, and
the lint pass over the tree they sit on reports ten findings, none of them in
the lines those commits wrote and all of them in the way the tree around them
is named, ignored or tested. They block the branch from landing, so they are
cleared here, in a round of their own, before the branch is released.

## What the lint pass finds

Run as `cargo mock --lint-only --strict`, ten errors, in four kinds.

Two `[no-runtime-spawn]` findings, both in `cache_tests.rs`. Each is a test
that holds a build lock on the main thread and runs `ensure_built` on a second
thread, to show that the second launcher waits while the first holds the lock
and finishes once it lets go. The lint forbids `std::thread::spawn` in the
stack, because concurrency there is scheduler-managed.

Five `[single-source/type]` findings, one per pair of crates that define a
public type of the same name. `Kind` is a trait in `renki-dirs` (a directory
kind: cache, state, config, data) and a trait in `renki-config` (a setting's
value kind: bool, int, text). `Sealed` is the private supertrait closing a
trait in each of the two. `Source` is an enum in `renki-dirs` (which of three
places named a root), an enum in `renki-config` (which of five places a
setting's value came from) and an enum in `renki` (where a tool's engine
comes from). `Resolved` is a struct in `renki-config` (a setting's resolved
view) and a struct in `renki` (a pin resolved to build attempts). Each pair
names two different concepts with one word, which is what the lint exists to
refuse.

Two `[catalogue-ignore/malformed]` findings in `retry.rs`. The two ignored
tests that stand for the prerequisite checks the design names and the code does
not do carry a reason that begins `catalogue:` and names the gap, and omit the
`; tracked #<id>` the lint asks for. Both gaps now have an issue on the
repository: 30 for the toolchain a checkout pins, 31 for the git source that is
unreachable.

One `[no-source-include-in-test]` finding at
`extension_tests/collecting.rs:247`. The test
`nothing_but_place_decides_how_material_is_placed` reads `extension.rs` with
`include_str!` and counts the lines that open the placement branch, to hold
that the branch exists once, in `place`, and not a second time in `locate`. The
lint says a check on source text belongs in a lint, which runs on every commit
and reads the parse.

## What this round decides

The decisions were made before the round opened and are recorded here as they
were given.

The names move and nothing keeps the old ones: no alias, no re-export, since
the crates are before 1.0 and carry no legacy to shim. In `renki-dirs`, `Kind`
becomes `DirKind`, `Source` becomes `PathSource` and `Sealed` becomes
`DirsSealed`. In `renki-config`, `Resolved` becomes `ResolvedView`, `Source`
becomes `Origin` and `Sealed` becomes `ConfigSealed`. `renki`'s own `Source`
and `Resolved` keep their names once the other crates' are renamed, since
nothing is left for them to pair with. `renki-config`'s `Kind` keeps its name
for the same reason. Where the lint still pairs two after the renames, the
narrower one is renamed and the round says which.

The two ignored tests gain `; tracked #30` and `; tracked #31`.

The placement property becomes a lint in `mock/lints/` that holds the same
thing the test held: the branch on `places_itself` appears once in
`extension.rs`, and inside `place`. It is shown failing on a copy of the tree
where the branch appears twice, and the text-reading test is then deleted.

The two spawns: where a thread is the honest way to hold a second launcher on
the lock, the lint's own allow line goes on it with a reason. A child process is
preferred when it tests the lock as honestly.

The design section "One build per key", which the branch's source already
describes in the module doc of `cache.rs`, is written into the design of
`renki`, since the design has none.

## Found while reading the lint, and not decided before

The `catalogue-ignore` lint also requires that every id after `tracked` resolve,
to a row of a ledger file the project names under `[lints.catalogue-ignore]` in
`ledgers`, or to a row of the registry. This repository names no ledger and
holds no registry rows, so `#30` and `#31` would pass the shape check and then
be refused as unresolved, which swaps one finding for two. A ledger is the
smaller answer, and the lint's own description says a project that means its
ignores tracked has to give them somewhere to be tracked. The round therefore
adds one ledger, listing the two issues, and names it in `mockspace.toml`. That
is the one addition beyond the recorded decisions, made because the decisions
cannot clear the findings without it.

The same reading settles the spawn. The two tests call `ensure_built` in this
process with a backend that is a type in the test module, so a child process
would have to be the test binary re-entering itself with a filter and an
environment variable to find its way back to the same call, which tests the
harness's re-exec more than the lock. A thread holds the second launcher with
the code under test unchanged, so the allow line is the honest answer, and the
two spawns share one helper so the allow and its reason are written once.
