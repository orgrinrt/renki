# ls-remote-answers-within-a-deadline

A defect, found in review of the same resolver written a second time in
mockspace's engine (mockspace#132), and present here first.

`pin::ls_remote_head` runs `git ls-remote` with `Command::output()`, which
waits for as long as git does. Two callers reach it: a branch pin being
resolved once its hour-old resolution has aged out, and `selfupdate`, which
asks for the launcher's own branch head at most once an hour. On a network that
drops packets rather than refusing them, a captive portal or a dead VPN, git
does not give up for a long time. An ad-hoc spike in that review had
`GIT_TERMINAL_PROMPT=0 git ls-remote https://10.255.255.1/x.git refs/heads/dev`
still running after 46 seconds when it was killed, so every launch in the hour
after the window closes stalls that long, and the offline fallback that exists
for exactly this case only starts after git gives up.

Two further ways the same call waits: https with a credential helper that
asks, which `GIT_TERMINAL_PROMPT` does not govern, and ssh with a key wanting
its passphrase and no agent. Both prompt from inside a launcher somebody ran
to get a tool, and nobody is expecting to be asked anything.

What the fix is:

- The remote gets a deadline, five seconds, after which the child is killed
  and the call returns an `Err` naming the deadline. Both callers already
  treat an `Err` as a remote that could not be reached, so nothing downstream
  changes.
- The call never prompts: `GIT_TERMINAL_PROMPT=0`, stdin closed, and ssh in
  `BatchMode` unless `GIT_SSH_COMMAND` is already set, since a clone that set
  it has said how ssh is to run.
- Both pipes drained on their own threads, so waiting on the child with a
  deadline cannot deadlock against a full pipe.

Five seconds because an answering remote replies to one `ls-remote` for one
ref in well under a second, and a second attempt comes an hour later anyway.

## Where the fix moved before the doc window locked

Three parts of the list above did not hold up once mockspace#132 was reviewed
with the same shape in it, and one does not fit this repository's lints.

- `GIT_SSH_COMMAND` is not the only thing that says how ssh runs. `GIT_SSH`
  and `core.sshCommand` do too, and git ranks `GIT_SSH_COMMAND` above both, so
  setting it over either throws away the key somebody chose there. Batch mode
  goes on only where none of the three is set, read in rank order through a
  trait so the command can be tested against a fake of all three.
- "Never prompts" was wrong where ssh is configured: that ssh is left alone and
  may ask on the terminal. The deadline is what holds it.
- Reading `core.sshCommand` is itself a `git` run, so it shares the five
  seconds with the listing rather than adding its own.
- Draining the pipes on threads needs `std::thread::spawn` and a boxed `dyn
  Read`, and `no-runtime-spawn` and `no-dyn-dispatch` refuse both here. The
  output goes to two scratch files instead, read back at the child's exit,
  which also stops a background process holding the output from holding the
  answer.
