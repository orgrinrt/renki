# reading-without-std

Where the reading of a manifest lives, reopened: the first decision of
`where-the-manifest-reading-lives` put it in a `std` crate, and the lints this
repository runs bind every crate but the launcher to `no_std`, no alloc and
the stack's types. Reading a file does not need `std`, and a TOML parser of
the stack's own could replace the two TOML crates renki carries, if it is
shown to read the newest TOML exactly.

## The intent

- The reading of a manifest passes `no-std`, `no-alloc` and the `no-bare-*`
  lints as they stand: no exemption, no allow-marker, no ratchet.
- File i/o without `std`, by a vehicle stated per platform renki supports.
- What no alloc means for a manifest of unknown size, said.
- The stack's own TOML parser in place of `toml` and `toml_edit`, a crate of
  its own in the repository that holds the stack's TOML work, generic, naming
  none of its users, held to the newest TOML specification by the official
  toml-test suite, valid and invalid cases both, with the number in the round.
- renki depends on that one crate and not on the rest of that repository; the
  crate is published before renki's next release candidate.
- Everything else of this round stands: the layers, the order, `meta`, the
  predicates, the merge and the POSIX reader.

## The two feasibility questions

Answered by two committed sketches before any design here.

1. `202611272130_no-std-file-reading-on-unix`: WORKS. A `#![no_std]`,
   no-alloc crate reads a whole file into a caller's buffer, lists a
   directory, reads a variable and runs `sh -c` in a directory with its exit,
   through the C library alone (the `libc` crate, default features off). It
   runs on x86_64 linux and builds with core only for linux gnu and musl,
   macOS on both architectures, freebsd, netbsd, openbsd and illumos, which
   are the platforms `renki-dirs` names. Only where errno lives differs per
   C library. A file's size is known from `fstat` before a byte is read, so a
   buffer too small is refused with the size it needs.
2. `202611272150_a-no-std-toml-parser-against-toml-test`: WORKS. A
   `#![no_std]` TOML reader with no alloc and no unstable feature, building on
   stable, passes every case the official suite carries:

   | spec  | valid     | invalid   |
   | ----- | --------- | --------- |
   | 1.0.0 | 208 / 208 | 501 / 501 |
   | 1.1.0 | 218 / 218 | 494 / 494 |

   from `toml-test-data` 2.14.1, compared through `toml-test` 2.1.0's own
   value equality. Two deliberate breaks turned 16 invalid and 6 valid cases
   red per version, so the harness sees what it claims to. The reader hands
   what it reads to a visitor, keeps its duplicate-definition index in a slice
   of nodes the caller gives (28 bytes a node, at most one per two bytes of
   text, 0.333 per byte the most the suite needed), and leaves strings as
   spans of the text, decoded on demand.

## Where the reading lives

1. In `renki-config`. It would stop being the contracts, and every call into
   the C library is `unsafe` code in a crate that reads nothing.
2. In `renki-manifest`, now `no_std`. Its own thing is reading a manifest off
   the disk; the contracts stay as they are.
3. A third crate for the C calls alone, under `renki-manifest`. A crate for
   one thing nothing else needs yet; a second user is when it is split out.

Decision: 2. `renki-manifest` stays, `#![no_std]`, no alloc, and passes the
lints as they stand. Its i/o is a `Host` trait with one implementation per
target family, over the C library through `libc`; a target with no
implementation does not build. The `unsafe` is in that one module.

## Memory

A manifest's size is not known until it is found. The caller gives the room,
`Room`, which holds the text of every layer read, back to back, and the
parser's index. A file that does not fit is refused with the size it needs, so
a caller with a fixed room learns how big to make it, and one with an
allocator gives one that size and reads again. Nothing is read twice in one
read: the size of each file is known before its bytes are.

## The parser

A crate of its own, `tomlfuse-parse`, in the tomlfuse repository beside
`tomlfuse-core`: `#![no_std]`, no alloc, stable, generic. It reads one
document from the caller's text, hands every table header, key and value to a
visitor, and refuses with the byte offset anything the spec refuses. The
sketch is its first draft. It is held to toml-test there, valid and invalid,
for every spec version the data carries.

renki depends on `tomlfuse-parse` alone. Since a git dependency keeps a crate
from publishing, `tomlfuse-parse` is published first, and renki's next
release candidate takes it from the registry.

The TOML store, `Toml`, is renki-config's `Store` over `tomlfuse-parse`, in
`renki-manifest`: it answers keys and shapes from the visitor's spans and
writes a key by editing the text at its span, so comments survive. `toml` and
`toml_edit` leave renki: every TOML file the launcher reads, its two
configuration files, a tool's descriptor, a crate's `Cargo.toml` and the
registry's rows, goes through the one parser.

## Merging without a tree

The merged view is not built: it is the stack of layers, answered key by key
by `renki-config`'s `stacked`. `Manifest::read::<T>` deserialises through
`serde` with its default features off, from a deserializer over the stack, so
a tool's type borrows its strings from the room. A type that wants owned
values owns them by its own allocator, never by the reader's. The dump walks
the leaves in byte order of their dotted path with the room's index, and
writes into a `core::fmt::Write` sink.

## What stays

The layers, their order, `meta`, includes to a fixed point, the predicates,
the merge rule and the POSIX reader, as `layers-meta-and-predicates` and
`the-posix-reader` decided. The one call stands, with the room as its one
more argument: `renki_manifest::read::<T>(path, &mut room)`.
