# a-new-revision-builds-from-its-own-sources

A branch pin that moved built nothing and ran the old engine. homma's `dev` went from f8fa8e7 to a3caf61, the launcher keyed the new revision and ran `cargo install --git ... --rev a3caf61 homma-engine` into its own key, and the install finished in two seconds with the f8fa8e7 binary hard-linked out of the shared build directory (`target/release/deps/homma_engine-4d7272db1757a251`, the same unit for both revisions). Removing that one fingerprint made `homma-api` the stale one in the same way, and the build went through only once every `homma-{api,core,engine,org,store}` fingerprint was gone. Every launcher on the machine ran the old engine until then.

The cause is cargo's, and two of its rules meet. `cargo install --git` checks the revision out under `$CARGO_HOME/git/checkouts/<repo>-<hash>/<short rev>/` and loads that checkout as a path workspace, so a package's unit is hashed by its path relative to the checkout's root, which is the same for every revision. And cargo never checks the modification times of what lies under `$CARGO_HOME`, since a checkout or an unpacked crate does not change, so the trace says `filesystem up-to-date` for a checkout written a minute after the unit. A unit of revision one is then fresh for revision two. Measured by the sketch `202611191642_a-git-install-reuses-another-revisions-units` (`probe.sh`, its run in `probe-output.txt`, cargo 1.98.0-nightly fbb61be30) with four revisions of a two-crate repository, `probe-a` on a path `probe-b`, installed with one `CARGO_BUILD_BUILD_DIR` and a root of their own each: every binary printed revision one's word, the fingerprint directories stayed one per package, `CARGO_LOG=cargo::core::compiler::fingerprint=trace` showed `all paths up-to-date` and `filesystem up-to-date` for the new checkout, and `--message-format json-render-diagnostics` reported both units `"fresh":true` with ids `path+file://<checkouts>/repo-<hash>/<short rev>/<dir>#<name>@<version>`. The same four revisions installed by `--path` from clones outside `$CARGO_HOME` each printed their own word, so the build directory is shared correctly wherever cargo checks the files.

Since 0.0.5-rc.2 every install compiles in the repository's build directory, so every attempt that names `--git`, a branch, a revision or a tag, is open to this. A version from the registry is not: its unit is keyed by the version, and two versions are two units.

What keeps the sharing and builds each revision from its own sources: the install of a `--git` attempt reports its units as cargo's JSON messages, and a unit of a path package that comes back fresh was taken from whatever this build directory compiled from that checkout's path before, which may be another revision. Where one does, the fingerprints of every path package of that install are removed from the build directory and the attempt runs again, which compiles them from this revision. The registry's units stay shared. An install that compiled every path package itself runs once. The cost of a key built twice for one revision, after its binary was evicted, is that second run, and it is correct either way.

A fresh path unit is the only signal, rather than a record of which revision last built a package, because a record cannot answer for a build directory it never saw: the container that met this had built the old engine before any record existed, and a repository's own `cargo build --release` of the same packages lands on the same units.
