# the-posix-reader

How a tool that cannot link Rust reads the same manifests, their layers and
their predicates, and how another repository takes only that reader.

## The intent

One reading of a manifest, held in renki, with a POSIX path beside the Rust
one; the two cannot drift because one suite of conformance and parity tests
runs both; a consumer takes the POSIX path from renki itself, at the same
revision its Rust side pins, and nothing else of the repository. Generating
the POSIX reader from the Rust was offered as a possibility, the suite as the
floor.

## How it is made

1. By hand, in POSIX `sh` and `awk`, held to one suite both readers run.
2. Generated from the Rust. No generator exists, and what would be generated
   is a TOML reader, a merge and a predicate evaluator, not a table of
   constants: the generator is a compiler from Rust to `awk`, bigger than its
   output.
3. An existing shell TOML library lowered to `sh`. The ones at hand are bash
   and call `taplo` or `yq`; renki would then depend on a bash library and on
   a binary a POSIX host may not have.

Decision: 1. The suite is what holds the two readers together, and it holds a
hand-written reader exactly as well as a generated one. A generator stays
open, worth its cost only if the suite shows drift it cannot catch. 3 is out:
a POSIX reader that needs bash and a TOML binary is not a POSIX reader.

## What it reads

The POSIX reader does not claim all of TOML. It reads a stated subset and
refuses, with the file and the line, anything outside it, so it never reads a
manifest wrongly: it reads it or says it cannot.

- In: comments, trailing ones included; `[table]`, `[dotted.table]` and
  `[[array.of.tables]]` headers; bare and dotted keys; basic strings with the
  escapes `\"`, `\\`, `\n`, `\t`; literal strings; integers; booleans; arrays
  of those scalars, on one line or over several.
- Out, refused by name: multi-line strings, inline tables, arrays nested in
  arrays, quoted keys, floats, dates and times, `\u` escapes.
- Arrays over several lines are in because hook manifests, the first the POSIX
  reader is for, write their command lists that way. A trailing comment is in
  because the Rust reader takes it, and a refusal there would be the two
  disagreeing on a file both can read.
- The layers, `meta.overlays.include` with the same glob rule, the order, the
  merge and the predicates are read in full: the subset limits the syntax of
  one file, never the behaviour across files.

## What it answers

The common answer of both readers is a dump of the merged view: one line per
leaf, `<dotted path> = <value>`, an array of tables indexed as `name[0]`, the
value in one canonical TOML form, the lines sorted bytewise. `get <key>` is the
dump's line for a key. The Rust reader gains the same dump, so both are
compared on the same bytes.

## The suite

One directory of fixtures, each a set of manifest files with its layers and an
expected dump, or an expected refusal. A fixture outside the subset carries
the Rust dump and the POSIX refusal. One test runs every fixture through both
readers and compares each with the fixture: conformance is each reader against
the fixture, parity is both meeting the same file. A behaviour lands in both
readers or the fixture that pins it is red for the one that lacks it.

## Where it sits

Everything the POSIX reader needs is under one top-level directory, `posix/`,
and it reads nothing outside it. A consumer adds renki as a submodule at a
pinned revision with a sparse checkout of `posix/`, and sources the reader
from there. The fixtures sit under `posix/conformance/`, so the same sparse
path carries them.

`sh` is the POSIX shell and `awk` the POSIX awk: no `local`, no shell arrays,
no `gawk` extensions. A shell predicate runs through `sh -c` the same as in the
Rust reader.

## A fixture per predicate kind

Both readers evaluate the same predicate kinds, so the suite carries a
fixture for each of `env`, `shell`, `not`, `all` and `any`, holding and not
holding, and `env` with each truthy and falsy word and a refused one. The Rust
reader runs the `shell` fixtures where its `shell-predicate` feature is on;
the POSIX reader runs them always, through the same `sh -c`.
