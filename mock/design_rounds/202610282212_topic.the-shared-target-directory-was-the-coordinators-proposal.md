# the-shared-target-directory-was-the-coordinators-proposal

A round that stands alone, the way a defect found and fixed does. The branch
`fix/one-engine-install-at-a-time` was reviewed after the round that cleared its
lint findings, and the review refused it on one blocking finding and four
smaller ones. All of them are in the branch's own lines, and they are fixed here,
forward, by editing the sites rather than reverting the commits that put them
there.

## What op asked for, and what was added

Op's intent for the job, 20:30: "a lock around every renki install, leaves no
temp directory behind". The intent is the lock and the absence of a leftover
directory. Nothing in it asks for a directory that persists between builds, and
nothing asks for more than one lock.

The shared cargo target directory was not op's. It was the coordinator's
proposal: "a build directory that persists so an interrupted build resumes".
That sentence is kept as it was said, as provenance. The intent in it is the
resume, which is worth keeping and which a per-key target directory gives too.
The one directory every key shares, and the second lock that came with it, are
the vehicle, and the vehicle is what the review found wanting.

## The six type names

The previous round renamed six public types so that no two crates define one
name: `DirKind`, `PathSource`, `DirsSealed` in `renki-dirs`, and `Origin`,
`ResolvedView`, `ConfigSealed` in `renki-config`. Those six names were the
coordinator's choices and not op's. What was asked was that the lint stop
finding two crates defining one name, and which names resolve that was left to
the work. They stand as proposals, and a different spelling is a rename away.

## What the review found

Blocking. Since `cc579cd` every key builds into one `<cache>/target`, and
`1042d69` put a second lock named `target` around the whole compile. That lock
waits with `file.lock()` and no deadline, and the wait covers the network fetch
of the install, so one hung `cargo install` blocks every launcher of that tool
on the machine, whatever its key. The only message is that another launcher is
building `target`, which names no key. The shared directory is also never
collected, which the module doc, the design and the readme each say as though it
were a decision.

The collector deletes `builds/<key>` without trying that key's lock, so a
collection pass that runs while a build is in progress can delete the directory
the build is writing into.

`CargoPlan::dir` is documented as a toolchain concern and not as the directory
the build runs in, and `<Cargo as Backend>::fingerprint()` reads rustc from the
process's directory while the build, and the key the launcher computes, read it
from the repository's root.

The `--engine` scratch build passes `dir: None`, so it builds under the toolchain
of the process's directory and not of the repository it is run for, which is
where the pinned builds build.

`builds_of_different_keys_take_turns_on_the_shared_target_dir` carries setup
that does nothing: it creates the `bin` directory, removes it and creates it
again.

## What this round changes

The target directory moves to `<builds>/<key>/target`, so an interrupted build of
a key still resumes, and the collector removes it with the rest of its key. The
`target` lock is deleted along with the test that held it, and the sentences
saying the directory is not collected are deleted from the module doc of
`cache.rs`, the design and the readme. The per-key lock and the waiter's re-check
after it stay as they are.

The collector takes the key's lock without waiting before it deletes the key, and
skips a key whose lock is held, leaving its row for the next pass. A test holds
the lock and runs a pass, and it is shown failing before the change.

`CargoPlan::dir` says that the build runs there. `fingerprint` on the `Cargo`
backend is a function of the type alone, in a trait that every backend
implements and the registry holds as a function pointer, so reading rustc from a
plan's directory would change the contract of a public trait for a method the
launcher does not call: the launcher takes its key from the repository's root
directly. The mismatch is documented on the method.

The scratch build is given the repository root.
