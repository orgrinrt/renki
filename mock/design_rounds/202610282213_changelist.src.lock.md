# src changelist

The source half of the round that answers the review of the one engine install
branch: each key builds into a target directory of its own, the one lock is the
key's, the collector tries that lock before it removes a key, and the scratch
build runs where the pinned builds run. Descends from the doc changelist
`202610282212_changelist.doc.lock.md` and the topic file
`202610282212_topic.the-shared-target-directory-was-the-coordinators-proposal.md`.

## CHANGE: the engine build's target directory FROM `<cache>/target, shared by every key under a second lock named target` TO `<cache>/builds/<key>/target, under the key's lock alone`
File: `mock/crates/renki/src/cache.rs`, `mock/crates/renki/src/cache_tests.rs`
Verification: `grep -c 'BuildLock::take' mock/crates/renki/src/cache.rs` is 1, inside `ensure_built`, and `grep -n '"target"' mock/crates/renki/src/cache.rs` returns the one line in `build_plan` that joins it onto the key's directory; the module doc of `cache.rs` no longer says the directory is shared or not collected, which `grep -n 'not collected\|shared target\|take turns' mock/crates/renki/src/cache.rs` shows by returning nothing. `builds_of_different_keys_take_turns_on_the_shared_target_dir` is gone with the lock it held, and the dead `remove_dir_all` and `create_dir_all` it ended its setup with went with it. `a_build_compiles_into_a_target_directory_inside_its_own_key` is green. `a_waiter_finds_the_binary_the_holder_built` is untouched and was shown red with the re-check after the lock disabled, and green restored.

## CHANGE: `Registry::gc` FROM `deleting builds/<key> without asking its lock` TO `trying the key's lock without waiting, skipping a held key and keeping its row`
File: `mock/crates/renki/src/registry.rs`, `mock/crates/renki/src/cache.rs`, `mock/crates/renki/src/registry_tests.rs`
Verification: `grep -n 'try_take' mock/crates/renki/src/registry.rs mock/crates/renki/src/cache.rs` returns the call in `gc` and the method on `BuildLock`, which shares its opening with `take`. `gc_leaves_a_build_in_progress_and_takes_it_once_it_is_done` holds the key's `BuildLock`, runs a pass, finds the key, its row and its `target` directory still there, lets the lock go and finds the next pass removes all three. It was run before the change with `BuildLock` made reachable and nothing else, and failed with `a build in progress was evicted: ["3333333333333333"]`; it is green with the change.

## CHANGE: `CargoPlan::dir` and `<Cargo as Backend>::fingerprint` FROM `a toolchain remark and no remark` TO `the directory the build runs in, and the directory the fingerprint is read in`
File: `mock/crates/renki/src/extension.rs`
Verification: `grep -n 'cargo is started with it as its working directory' mock/crates/renki/src/extension.rs` returns one match on the doc of `dir`, and `grep -n 'Read in the launcher.s own directory' mock/crates/renki/src/extension.rs` returns one match on `fingerprint`. The fingerprint is not changed to read a plan's directory: `Backend::fingerprint` takes no plan and `Registered` holds it as a function pointer, and `grep -n 'rustc_fingerprint' mock/crates/renki/src/lib.rs` shows the launcher's key reading the repository's root directly.

## CHANGE: the `--engine` scratch build FROM `dir: None, the process directory's toolchain` TO `the repository root, as the pinned builds have`
File: `mock/crates/renki/src/engine.rs`, `mock/crates/renki/src/lib.rs`
Verification: `grep -n 'dir:        None' mock/crates/renki/src/engine.rs` returns nothing, and `grep -n 'repo_root' mock/crates/renki/src/engine.rs` returns the parameter of `build`, its doc and the plan's `dir`; `build` makes the cache root absolute first, since cargo now resolves `--root` and `--target-dir` in another directory, and `lib.rs` passes the discovered root. `cargo test -p renki` is green.

## Not changed, and why

The per-key lock and the waiter's re-check, as asked. A finished build keeps its
`target` directory until the collector removes the key; the review asked for
the directory to go with its key, and deleting it at the end of a successful
build is a further change this round does not make.
