# one-copy-of-every-built-engine


Op, 15 November: "There's no room for more than exactly one of each built part at a time on these discs. Any second instance of same bytes is wasted space and an error requiring immediate fix ... Same goes for homma. Then after that, same goes for all the tooling built on either". The intent is that a build leaves exactly one copy of every byte it makes; the rest of the quote is kept for provenance. The plan it belongs to is the workspace's `.shared/research/202611152000_one-copy-of-every-built-byte/README.md`, items M1 and H2.

Two places in renki keep a second copy.

The first is the target directory. Each key installs through `<cache>/builds/<key>/target`, the `--engine` scratch build through `<cache>/engines/<hash>/target` and the launcher's own reinstall through `<cache>/launcher/target`, and none of them is ever removed while its build stays. Each holds every compiled dependency again, most of which the consuming workspace has already built into its own target, and a copy of the installed binary besides. Measured on the workspace: 607M for mockspace's engine and 557M for homma's.

The fix is that a build compiles its intermediates where the consuming repository's cargo would, and keeps nothing of its own once the binary is installed. Cargo has the split built in: `build.build-dir` holds the intermediates and the target directory only the final artifacts. `cargo install` reads no project configuration, only `$CARGO_HOME`'s, so it never learns the consumer's directory by itself. The launcher already runs the build in the repository's root, so it reads cargo's configuration from there, the way a `cargo build` in that root would (the variables first, then each `.cargo/config.toml` from the root upward, then `$CARGO_HOME`'s), takes `build.build-dir` or else the target directory, and hands it to the install as `CARGO_BUILD_BUILD_DIR`. The tool then has nothing to pass: a repository whose cargo shares one build directory shares it with the launcher too. Where nothing is configured the install compiles in its private target as before. Either way the private target is removed once the binary is in place, so what stays in the cache is the binary. A killed build keeps its target and resumes, since only a finished install removes it. A key built by an earlier launcher has its target removed on the next run that finds the binary, under the key's lock.

The second is the collection of superseded builds. The collector removes a build no repository resolves to, but only in the pass it throttles to once a day, so a branch pin moving through three revisions in a day kept three engines of 21.6 MB each. A repository re-resolving to a new key leaves the old key with no consumer the moment the registry records it. So the removal of a build no consumer resolves to runs on every recording, not on the daily pass; what is still pinned somewhere stays, and the retention window keeps its daily pass. That keeps one binary per pin in use.
