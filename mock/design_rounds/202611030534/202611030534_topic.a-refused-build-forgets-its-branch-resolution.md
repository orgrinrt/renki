# a-refused-build-forgets-its-branch-resolution

## Current state

A branch pin resolves to the tip of the branch through `pin::resolve_branch`. The answer is recorded under the cache root with the time it was made, and a recording younger than `BRANCH_TTL`, an hour, is used without asking the remote again. When the remote cannot be reached, a recording of any age is used instead, on the reasoning that the revision it names was the tip not long ago and is probably built and sitting in the cache.

The build of the resolved revision comes next, in `cache::ensure_built`. When that build fails, nothing touches the recording. Every launcher that resolves for the next hour reads the same recorded revision and builds it again, so a branch that was broken for a minute and fixed a minute later stays unusable for the rest of the hour, from every checkout that pins it. The report that started it is the ticket `renki_keeps_a_branch_resolution_whose_engine_build_failed_fo`.

The first attempt at this, a single commit on `work/tooling-track-renki-forget-failed-resolution`, forgot the recording on any error from the build. It had no round, returned an anonymous four-tuple from the function that pairs the resolution with the build, and claimed five mutants caught with nothing committed to show them. This round redoes it on top of the deadline work, whose design text for the fallback says a branch pin falls back to its last resolution and does not yet say when that last resolution is gone.

## What a failure may forget

Which failures say anything about the revision is the question the round exists for, and the options were these.

First, every error out of the build. This is the first attempt. A build that never started, because cargo is not on `PATH` or the key's lock could not be taken or the directory could not be made, says nothing about the revision, and forgetting then costs the recording for nothing. Offline with no cargo, the next run would report the remote unreachable and not that cargo is missing, which is the wrong message for the operator to fix first.

Second, only a build that started and was refused: cargo ran and every attempt failed, or succeeded and left no binary. This is what the revision can be blamed for. It is not exact, because cargo also fails when the network drops while it fetches a dependency, and that looks the same from here. Forgetting then costs one `git ls-remote` on the next run, bounded by the five second deadline, and loses no fallback: the revision that failed has no binary in the cache, so falling back to it offline would fail in the build again.

Third, never forget, and shorten `BRANCH_TTL`. This keeps the broken-window symptom for as long as the shortened time and gives every run that has nothing wrong the cost of the remote ask.

Fourth, ask the remote before every build of a recording older than some small age. This also changes every healthy run.

The second is taken. The first forgets on things that are not the revision's fault, the third and fourth tax the runs that were never broken, and the second's one inexactness costs a single bounded ask.

## How the difference is carried

The two kinds of failure are told apart by a type and not by reading the message. A crate-private `BuildError` has `NotStarted` and `Refused`, each holding the message the operator reads. `Cargo` builds through a function returning it, `install_with_retry` produces `Refused` from the failure it already assembles, and `cargo_is_on_path` and the failure to spawn cargo produce `NotStarted`.

The public `Backend::materialise` keeps `Result<(), String>`. Its error being text is a known gap that waits for the stack's string type and is marked where it is declared, and changing a public contract for a crate-private distinction would put every backend's author in this round. `Cargo`'s implementation of it turns a `BuildError` into its message. `ensure_built`, which is the launcher's own and chosen at compile time, reaches the typed function through `place`, which becomes generic over its error so that `materialise_once` still answers `String`.

The function that pairs a resolution with its build returns a named `Built` and not four values in a tuple: the resolution, the toolchain, the key and the binary. A `Refused` removes the recording of that url and branch through `pin::forget_resolution`; a `NotStarted` does not. Other branches of the same remote keep their recordings, a pin that names no branch has none to remove, and a build that worked keeps its own.

## What the round changes

The text in the design for asking a remote for a branch head says a branch pin falls back to its last resolution when the remote cannot be reached. That stays true and gains its exception, in the same place: a build that was refused removes the resolution, so the fallback never offers a revision that is known not to build. A section on the forgotten resolution carries the rest.

The mutants of the new code are a table with its log, committed beside the round, because a count of mutants caught that nothing shows is a claim and not a result.

Out of scope: the window in which the remote answers a revision the branch has since moved past, which is the hour the recording exists to bound.
