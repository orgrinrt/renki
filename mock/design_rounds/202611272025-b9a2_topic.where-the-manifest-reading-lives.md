# where-the-manifest-reading-lives

Which crate reads a manifest off the disk with its layers, what stays a
contract, and what the tool descriptor gains in the same round.

## The intent

Every manifest of the tools built on renki is read by one owner: a base file
`name.ext`, any number of layers `name.<layer>.ext` merged over it in an
order the base can change, a `meta` table steering the reading, and named
predicates saying when a layer applies. A tool gets all of it by taking that
owner and writes no reader of its own. That holds for a launcher's two
configuration files, an engine's manifest, and the manifest of a tool renki
does not launch at all; and a tool that cannot link Rust reads the same files
through a POSIX path held to the same behaviour (`the-posix-reader`).

## The question

The locked design of round 202609041058 makes `renki-config` the contracts:
`no_std`, no alloc, it reads no file and no environment. The TOML store and the
reading of the two files are in `renki`, the launcher library. Layering needs a
directory listing, globbing over the disk, every layer's text, the environment
and, for a shell predicate, a process. None of that is `no_std`.

Three places it could go:

1. A `std` half of `renki-config`, behind a feature. Changes a locked design,
   and the crate stops being what its name and readme say: the contracts.
2. The `renki` crate does discovery and layering. Every user then takes the
   launcher library, its build cache, its pin and its exec, to read a file.
   That is one crate holding two things, and the reason `renki-dirs` was split
   out of it.
3. A new crate beside the two. One more crate to publish, and the TOML store
   moves into it out of `renki`.

## Decision

Option 3: a crate `renki-manifest`, layer L1 beside `renki`, `std`.

- It holds what reads a manifest off the disk: finding the layers of
  `name.ext`, following `meta.overlays.include`, reading every layer's text,
  answering a predicate from the environment or a process, merging the layers
  into one view, the dump both readers answer in, and the TOML store, moved
  here from `renki::config` with its writer.
- `renki-config` stays the contracts and grows the parts that are logic and no
  i/o: the layer's name read off a file name, the order, the `meta` schema read
  through any `Store`, the predicate as a type and its evaluation over a
  caller's answers, the glob match, the merge rule, the stacked lookup the
  resolver reads, and the layer in the provenance. Each is the one owner of its
  rule, so the typed settings and a deserialised manifest cannot read a layer
  two ways.
- `renki` takes `renki-manifest` for its two configuration files and keeps the
  `--cfg` flag, the variables handed to the engine and the `config` verbs. Its
  `config::toml` module goes; the store's path is `renki_manifest::Toml`. No
  alias is kept, pre-1.0.
- A user that only reads a manifest takes `renki-manifest` and `renki-config`
  and nothing of the launcher.

Not 2: what a crate is for decides where a thing lives, and the launcher is for
launching. Not 1: the logic half fits the contracts as they stand, and the i/o
half is exactly what they exclude.

## The TOML store as it moves

The store parses all of TOML through `toml_edit` and answers less: an array of
tables and a float come back `Isnt` (`renki/src/config/toml.rs:214-227`),
`keys` skips arrays of tables (`:229-241`), a list's string items keep their
escapes undecoded (FIXME at `:306`), and the writer reads a `[[x]]` header as
no section (`:139`). A manifest is mostly arrays of tables, so the store that
moves answers them, decodes its items, and its writer knows `[[x]]`. One
parser, `toml_edit`, serves the store, the merge and the deserialising, so a
manifest is never parsed two ways.

## The descriptor: who, moment and settings

`tool.toml` is `renki::extension::Descriptor`, which refuses unknown fields,
so what a host wants its tools to declare is renki's to add.

- `who`: a list of words naming whom the tool is for. renki keeps them and
  interprets none; a host matches them against its own roles.
- `moment`: one line saying when the tool is reached for. Text, kept and shown.
- `settings`: rows of `key`, `kind`, `default`, `scope` and `doc`, the shape of
  `renki-config`'s `Setting`, read from TOML. The kinds offered are the ones
  whose parsers need nothing but the text: `bool`, `int`, `text`, `path`,
  `list` of text. A `choice` takes its options from a type, so a descriptor's
  `choice` is refused by name.
- To carry rows read at run time, `Declared` takes a lifetime for its strings,
  `Declared<'a, St>`; a launcher's static table is `Declared<'static, St>`. The
  parsers stay function pointers, chosen from the kind's name.
- Where a hosted tool's values come from is the host's: it resolves the rows
  over the documents it names, through the same resolver, and the tool gets the
  result as `<NAME>_CFG_<KEY>`, the descriptor's `name` as the short name, the
  way a launcher hands its engine `<SHORT>_CFG_<KEY>`.
