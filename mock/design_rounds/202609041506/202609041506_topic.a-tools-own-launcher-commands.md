# a-tools-own-launcher-commands

The launcher answers two things without the engine, `locate` and `config`,
and both are renki's own: fixed names, fixed output, declared by the crate
rather than by the tool. The second consumer of the configuration design,
homma, wants a third that is not renki's at all. `homma workspace` reports
the workspace the cwd is in, or spawns one where it is not, and the spawning
case is the whole point: there is no `homma.toml` above the cwd, so there is
no root, no engine to resolve and nothing to exec. The engine cannot answer a
question about a workspace that does not exist yet.

So the descriptor gains a table of commands the launcher answers itself,
each a name, a sentence and a function, and the run loop tries them where it
tries `config`: after the launcher's own flags come off, before a root is
required. The function gets what the launcher knows at that point, which is
the tool, the cwd, the root where one was found, the settings resolved from
the person's file and the repository's, and the arguments after the name. It
answers with the same `Result<(), String>` the hooks answer with, and the
launcher prints the refusal and exits nonzero, the way it does for `config`.

## What the settings look like from there

The resolved table was `pub(crate)`, one row per setting with the canonical
text and the source, because only the engine environment and `config get`
read it. A command reads it too now, so the row goes public with accessors
and nothing else changes about it: the text is the kind's canonical form,
the same bytes the engine would read out of `<SHORT>_CFG_<KEY>`, and a
command parses it through the kind the way an engine does. A list comes back
as `["~", "/srv"]` and `TextItems` walks it.

## What the descriptor check owes

A command name is a subcommand, so the same things that are wrong for
`locate.subcommand` are wrong for it: empty, and the launcher matches every
bare argument; the same as `locate`'s, or `config` where the tool has
settings, and one of the two is unreachable, decided by whichever the loop
tries first. Two commands with one name is the same defect between
themselves. `Tool::defect` is const and refuses all of it at build time,
which is where a descriptor is settled.

## What it does not do

A command is not a hook. It does not run on every invocation, it does not
see the pin, and it cannot reach the engine, since the engine may not be
buildable where it runs. A tool wanting to add a subcommand that runs the
engine adds it to the engine. What this is for is the question the engine
cannot be asked, and the two the crate already answers are the shape of it.
