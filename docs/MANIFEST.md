# renki-manifest. Design

What reads a manifest off the disk. Every rule it applies, which file is a
layer, the order, the `meta` table, the merge, the predicate, the glob, is
`renki-config`'s and asked of it; this crate does the i/o those rules need and
nothing else. A tool that only reads its manifest takes this crate and the
contracts, and nothing of the launcher.

## Finding the layers

`Manifest::find` takes the base's path. It reads the base and, where there is
one, `name.defaults.ext`, then lists the base's directory and keeps every file
`renki_config::layer_of` calls a layer. From each layer it reads, and from the
base and `defaults`, it reads `meta` first and follows `meta.overlays.include`:
each entry relative to the file that names it, a directory where it ends in
`/` (its files listed, the layers among them kept), else a glob matched with
`renki_config::glob_matches` against the entries of its directory. A file an
entry matches that is no layer of this manifest is refused by name.

Following goes to a fixed point. A layer whose `meta.when` does not hold is
not read, and its includes are not followed. A file reached twice, by any
path, is read once, by its canonical path, so an include cycle ends by itself.
Two files carrying one layer word are refused, naming both. The layers then
take their places by `renki_config::Order`, lowest first: `defaults`, the
base, the rest by `Order::rank`.

A layer in `meta.overlays.untracked` is checked against git where the
manifest's directory is in a work tree, once per find for all such layers: one
that git tracks is refused, naming the file and saying
`git rm --cached <file>`. Nothing is written to `.gitignore`. Where the
directory is in no work tree, nothing is checked.

## Answering the predicates

`Ambient` is this crate's `renki_config::Answers`: the process environment for
`Env`, and for `Shell` a `sh -c` in the manifest's directory with its exit
answered. The shell half is behind the feature `shell-predicate` and the unix
targets; a manifest that names a shell predicate on a build without it is
refused by name. `holds` runs every time a use site is read; this crate keeps
no answer.

## Merging and the schema

`Manifest::view` merges the read layers into one `toml_edit` document, lowest
first, asking `renki_config::meet` at every key and applying `meta.replace`
and `meta.unset` as it says, and keeps beside it which layer last set each
key. The merged view carries no `meta`.

`Manifest::read::<T>` deserialises the view into the tool's own type through
`serde`. A tool's type refuses unknown fields; a refusal from the type names
the key and, from the provenance, the layer and file that hold it, so one
schema holds across every layer and an unknown key is refused in whichever
layer wrote it. `Manifest::stack` hands the read layers to
`renki_config::resolve` for a tool's typed settings, which reads them through
the same documents.

## The TOML store

`Toml` is `renki_config::Store` over `toml_edit`, moved here from the launcher.
One parser serves the store, the merge and the deserialising, so a manifest is
never parsed two ways. It answers every value an array of tables holds, as
`name.0.field`; a list's string items come back decoded; the shape of a key is
answered for `meet`. Its writer edits the text line by line rather than
reserialising, so a person's comments survive every `config set`, and a
`[[name]]` header is a section to it.

## The dump

`Manifest::dump` writes the merged view as the one text both readers answer
in: one line per leaf, `<dotted path> = <value>`, an array of tables indexed
as `name[0]`, the value in one canonical TOML form (a basic string with `\"`,
`\\`, `\n` and `\t` escaped, an integer, `true` or `false`, a one-line array),
the lines sorted bytewise. `get <key>` is the dump's line for that key.

## The POSIX reader

Under `posix/` at the repository's root, beside the crates, and reading
nothing outside it: `posix/manifest.sh`, a library of POSIX `sh` to source,
and the `awk` it runs. It answers `dump <file>` and `get <file> <key>` in the
dump's bytes, and applies the same layers, include rule, order, merge, meta
and predicates.

It reads a stated subset of TOML and refuses, with file and line, anything
outside it, so it reads a manifest right or says it cannot. In: comments,
trailing ones included; `[table]`, `[dotted.table]` and `[[array.of.tables]]`
headers; bare and dotted keys; basic strings with `\"`, `\\`, `\n` and `\t`;
literal strings; integers; booleans; arrays of those, on one line or several.
Out: multi-line strings, inline tables, nested arrays, quoted keys, floats,
dates and times, and `\u` escapes.

A consumer that cannot link Rust adds the repository as a git submodule at a
pinned revision, checks out `posix/` alone, and sources `posix/manifest.sh`;
the same revision is what its Rust side pins.

## The suite

`posix/conformance/` holds one directory per fixture: the manifest's files
with their layers, a `dump` file with the expected dump, or a `refused` file
with the expected refusal's line. A fixture outside the POSIX subset holds
both: the dump the Rust reader answers and the refusal the POSIX reader gives.
One test of this crate runs every fixture through `Manifest::dump` and through
`posix/manifest.sh`, and compares each with what the fixture holds. Each
reader is checked against the fixture, and both against the same bytes, so a
behaviour lands in both readers or the fixture that pins it is red for the
one that lacks it. The fixtures sit under `posix/` so a consumer's sparse
checkout carries them too.
